# x-tunnel 流量整形与抗检测优化方案

状态:研究稿。针对"自定义二进制协议 over TCP + 首包 padding + 静默丢弃 + 单 TCP 长连接多路复用 + 可协商加密(ChaCha20/AES-128-GCM/XOR)"这一待优化协议。
参考基线:仓库现有 `wss://` + TLS 1.3 + ECH + smux 方案(见 `docs/protocol.md`)。
说明:本文无法联网检索(websearch/tavily 均不可用),结论基于公开研究与社区报告的既有知识;标注"社区报告"的条目未经官方确认,落地前应用自有拨测点复核。

## A. GFW/审查者常用检测手段 与 本协议暴露点

### A.1 检测手段清单

1. **首包长度指纹(first packet length fingerprint)**
   TCP 三次握手后,客户端发出的第一个数据包长度是强分类特征。历史上 Shadowsocks、SSH 等都因首包长度分布集中而被指纹。机器学习分类器通常把"包长序列 + 到达间隔序列"作为输入,首包长度是其中权重最高的特征之一。

2. **TLS 指纹(JA3 / JA4)**
   JA3 对 ClientHello 的版本、cipher suites、扩展列表、椭圆曲线、点格式做哈希;JA4 是其改进版(更抗扩展顺序扰动)。GFW 自 2021 年前后用 JA3/JA4 类指纹封过一批 VPN/代理客户端。**关键点:Go `crypto/tls` 默认 ClientHello(无 GREASE、扩展顺序固定、ALPN 形态)与真实浏览器差异明显,其 JA3 早已是公开可识别指纹。**

3. **SNI / ECH**
   - SNI 是 GFW 的主力封禁维度:按关键词过滤 SNI、按 SNI 关联封 IP。
   - **ECH 现状已反转**:2024 年起有研究观察到 GFW 主动识别并阻断携带 ECH 扩展的 ClientHello(或对发布 ECHConfig 的域下手)。也就是说,"用了 ECH"本身从加分项变成了红旗。**现有 x-tunnel 默认开 ECH,这在当前是一个净负债。**

4. **时序特征(timing)**
   包到达间隔、突发结构、心跳周期性。隧道类流量的 keepalive/ping 有固定周期,是明显的周期信号;交互式流量的突发节奏也可被学习。

5. **主动探测(active probing)**
   GFW 对可疑服务器主动发包:重放抓到的流量、发送垃圾数据、发送构造的 TLS ClientHello(随机/不存在的 SNI、畸形握手),观察服务器响应内容与时延。2015 年 Shadowsocks 即因"收到垃圾后解密失败并异常断连"与真实服务行为不同而被识别。

6. **流量熵分析(entropy)**
   加密载荷熵接近 8 bit/byte;真实 Web(HTTP/1.1 明文头、HTTP/2 的 HPACK)熵明显更低。全加密、无明文的流在熵特征上异常。**XOR 这类弱算法还会因密钥重复产生可检测的周期性/偏置。**

7. **双向流量相关性分析(bidirectional correlation)**
   审查者把入向流与出向流做配对,计算字节比、时序互相关。代理隧道的典型特征:**单条长连接、持续双向、吞吐高、上下行都饱满**。而正常浏览高度不对称(以下行为主)。多路复用把多条内部流聚合成一条外部长连接,聚合后的"持续双向 + 高吞吐"本身就是代理签名。

### A.2 本协议逐点暴露评估

| 协议特性 | 对抗效果 | 暴露点 |
| --- | --- | --- |
| 首包 padding(动态) | 打破固定握手长度指纹 | 若 padding 分布静态/区间窄,分布本身成为新指纹;融合后首包若恒大于真实 Web 首包(ClientHello ~517B),仍可区分 |
| 校验失败静默丢弃 | 抗内容型主动探测 | "端口对任何合法 TLS/HTTP 都永不回应"本身可被差异探测识别;静默的时延若与正常处理不一致,构成时序 oracle |
| 自定义二进制 over TCP(无 TLS) | — | **最大暴露点**:443 上无 TLS = 立即异常;其他端口高熵二进制 = "未知加密协议",正是分类器重点标记对象 |
| 单 TCP 长连接 + 多路复用 | 减少连接数 | 长连接 + 持续双向 + 周期性 ping → 时序/形态指纹;与正常浏览的不对称性相反 |
| 可协商 ChaCha20/AES-128-GCM/XOR | ChaCha20/AES-GCM 熵正常 | **XOR 应删除**:弱熵、密钥重复偏置,可被熵/重复分析识别 |
| 无伪装层 | — | 无 JA3(因为无 TLS)不是优势,而是"缺失正常协议特征"的异常信号 |

**结论:本协议当前形态在 GFW 视角下是"高熵 + 无 TLS + 长连接 + 双向饱满"的未知协议,属于最容易被分类器标记的一类。首包 padding 只解决了最表层的一个指纹。**

## B. 仅首包 padding 的不足 与 per-packet 策略的成本收益

### B.1 为什么首包 padding 不够

1. **后续包长度分布仍是指纹**
   分类器吃的是整条流的包长序列。首包模糊后,后续记录长度仍直接反映内层应用:交互式 SSH/聊天产生大量小包,视频/下载产生贴近 MTU 的大包,HTTP 请求产生特征性中等包。真实 TLS 应用的记录长度有自身分布(≤16KiB 的 TLS record、HTTP/2 frame 切分),隧道流的分布与之不重叠即可被学习。

2. **消息边界泄漏**
   长度前缀分帧若不 pad,等于把内层消息大小直接写进包长序列。多路复用下,smux 帧头 + 流 ID 的固定结构还会在长度/时序上留下复用协议自身的指纹(连接建立瞬间的帧序列尤其明显)。

3. **突发模式(burst pattern)**
   页面加载、TLS 握手都有特征突发形状(如 ClientHello→ServerHello→Cert 的三连发尺寸)。隧道把内层突发原样转发,突发形状被保留;聚合多条流后突发被"平滑",但平滑本身又变成另一种与单用户浏览不符的形状。

4. **时序相关性不因 padding 消失**
   padding 改的是尺寸维度,到达间隔、RTT 回显、双向互相关完全不受影响。

### B.2 三类对策的成本与收益

| 策略 | 做法 | 成本 | 收益 |
| --- | --- | --- | --- |
| per-packet padding | 每条记录 pad 到目标分布(如模仿 HTTPS 记录长度;或 pad 到 1200~1400B 贴近 MTU) | 小包场景带宽开销可达 20%~100%;需要缓冲,增加少量时延 | 对"包长序列"类分类器有效;对抗尺寸直方图分析 |
| 分段混淆(fragmentation/coalescing) | 大消息切成 ≤1200B 块(避免 IP 分片,模仿 TLS record/QUIC datagram);小消息合并批发送(Nagle 式,但按目标尺寸批) | 实现复杂度中等;合并引入 5~30ms 级时延 | 隐藏消息边界,使包长分布可控 |
| 流量填充(cover traffic / pacing) | 空闲期注入填充流;发送端按目标速率整形(pacing)加抖动 | 带宽成本高(空闲填充可数倍于真实流量);pacing 伤交互时延 | 对抗时序分析与突发形状;RegulaTor/Conjure 一类学术方案证明有效但昂贵 |

学术参照:traffic morphing(Houmansadr 等)、Mockingbird、Tamaraw、BUFR(缓冲整形)、RegulaTor(调节器式填充)、Gloves、Conjure 的抗指纹设计。共同结论:**尺寸整形便宜且对尺寸特征有效;时序整形昂贵且只能部分奏效;两者必须叠加,单做任何一项都会被另一维拆穿。**

### B.3 Trojan / VLESS-Reality / TLS-in-TLS 的教训

1. **Trojan**:外层真 TLS(合法证书),但内层是固定形状的 HTTP-like 载荷;证书/SNI 与真实站点不匹配时,主动探测 + 流量分析可识别。教训:**只包一层 TLS 不够,载荷形态与站点一致性同样会被查。**

2. **VLESS + Reality(XTLS)**:思路是字节级模仿真实 TLS 服务器——"偷"目标真实站点的握手,未授权访问者看到的是真实站点的证书与响应,因此抗主动探测最强。教训:**伪装必须做到 TLS 字节级完整**(包括服务端响应的 JA3/JA4、证书链、时延),且要持续跟踪真实浏览器指纹变化,维护成本高。

3. **TLS-in-TLS(XTLS Vision)2025 年被检测案例(社区报告)**
   2025 年上半年大量 Vision/TLS-in-TLS 服务器被快速封禁,社区归因(未经官方确认)集中在:
   - 主动探测:GFW 发送构造 ClientHello(随机 SNI/畸形握手),代理在异常输入下的响应内容或时延与真实站点不一致;
   - 外层握手指纹:外层 ClientHello 由 Xray/utls 生成,JA3/JA4 与真实浏览器不符;
   - 双层握手的记录尺寸/时延序列:内层握手叠加在外层之内,产生可统计的形状异常。
   教训:**"TLS 里面再套 TLS"这种双层结构会引入新的尺寸/时序形状;即使每层单独看合法,组合形状仍可指纹。任何"协议套协议"的设计都要把组合后的整体形状当作指纹面来审视。**

对本协议的直接推论:首包融合 + padding 是正确方向,但必须扩展到全流:后续记录尺寸分布、消息边界、突发形状、时序抖动都要整形,否则只是把指纹从首包挪到了后续包。

## C. 伪装路线对比

### C.1 路线一:自定义二进制协议 over TCP(本协议现状)

- **检测风险:高。** 无 TLS、无已知协议签名、高熵载荷,是"未知加密协议"的典型画像,正是分类器重点标记对象。在 443 上无 TLS 尤其反常;换到其他端口则端口本身可疑。
- **维护成本:低。** 无证书、无域名、无 TLS 栈复杂度,实现简单。
- **评价:成本最低但隐蔽性最差。** 只适合无审查环境或一次性/短命链路,不适合作为长期抗审查主力。

### C.2 路线二:伪装成标准 TLS 应用(WebSocket / HTTP2 / Reality)

- **WebSocket over TLS(wss)**:看起来像正常 HTTPS;但 WS 的 upgrade + 帧结构有自身形态,GFW 可经流量形态识别;仍远好于裸二进制。现有 x-tunnel 即此路线。
- **HTTP/2 over TLS**:与真实 Web 融合度最好;但需要有效证书 + 域名,SNI 可见(除非 ECH,而 ECH 现已被标记)。
- **Reality(VLESS Reality / XTLS)**:字节级模仿真实站点,抗主动探测最强;但需精心选择 dest/SNI,且要持续跟进真实浏览器 TLS 指纹,2025 案例显示此类方案也会随时间退化。
- **检测风险:中~低。维护成本:中~高**(证书/域名管理、指纹跟进、站点一致性)。
- **评价:对抗 GFW 的性价比最高的主力路线。**

### C.3 路线三:QUIC 伪装(TUIC / Hysteria2 / HTTP3)

- QUIC over UDP;GFW 历史上对 443/UDP 做 QoS 限速甚至阻断,吞吐受损。
- QUIC initial 包格式、版本号、ALPN/证书形态是已知指纹;Hysteria2 的"伪 TLS over UDP"已被指纹过;TUIC 握手是标准 QUIC 但 ALPN/证书可识别。
- UDP 本身在多审查环境天然可疑。
- **检测风险:中~高(UDP 可疑 + QoS 限速)。维护成本:中。**
- **评价:适合追求低时延/弱网穿透,但作为抗 GFW 主力不如 TLS 路线。**

### C.4 汇总对比

| 路线 | 检测风险 | 维护成本 | 抗主动探测 | 吞吐/时延 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 裸二进制 over TCP | 高 | 低 | 弱 | 最好 | 无审查/短命链路 |
| TLS 应用伪装(wss/HTTP2/Reality) | 中~低 | 中~高 | 强(Reality) | 好 | **抗 GFW 主力** |
| QUIC 伪装 | 中~高 | 中 | 中 | 低时延/弱网好 | 弱网/低时延场景 |

**建议:主力走 TLS 应用伪装;裸二进制只作为可选高性能模式,且必须外包一层"模仿 TLS 记录尺寸/时序"的整形;ECH 谨慎使用或默认关闭(当前是红旗)。**

## D. 被动 + 主动探测防御 与 IP 被封运营对策

### D.1 静默丢弃之外还需要什么

1. **静默丢弃是必要但不充分。** 端口对任何输入都静默,配合"合法客户端却能连通",GFW 可做差异探测区分。更稳的是**让未授权访问者看到真实内容**。
2. **蜜罐/真实站点 fallback(最推荐)**:服务器前置一个真实网站(Reality 式 destOverride,或真实 Web 服务兜底)。未授权探测者拿到的是合法站点的证书、响应与时延,主动探测无从下手。这是对抗主动探测的最强手段。
3. **延迟响应/时延整形**:响应时延要模仿真实服务器处理延迟并加抖动;避免 0ms 秒回或可疑的固定时延。鉴权失败的静默时延应与正常处理时延一致(HMAC 用常数时间比较),避免时序 oracle。
4. **不泄漏协议状态**:已做静默丢弃是对的;同时确保鉴权失败与成功在外部可观测行为(时延、字节数)上不可区分。

### D.2 服务器 IP 被封的运营对策

- **多 IP / DNS 轮询**:一个域名挂多个服务器 IP,DNS round-robin,客户端健康检查 + 自动故障切换。
- **快速轮换**:预置备用 IP/实例,检测到封禁立即切换;用境内/邻近拨测点持续探活,主动发现封禁。
- **降低单 IP 暴露**:控制单 IP 流量规模、保持良性流量形状,选信誉好的机房,避免流量过度集中。
- **真实业务同址**:在被封 IP 上同址跑真实服务,提高误封成本(附带损害威慑)。
- **域前置 / CDN 前置(谨慎)**:可隐藏源站,但多数 CDN 禁止隧道,需评估条款与可用性。
- **监控闭环**:把"连通性探测 + 封禁告警 + 自动轮换"做成运营基线,而不是事后人工处理。

## E. 推荐的流量外形方案

### E.0 总体结论

**把"自定义二进制 over TCP"降级为可选高性能内核,主力外形改为 TLS 应用伪装;无论走哪条路线,都按"首包拟形 + 后续记录整形 + 时序抖动 + 真实站点兜底 + IP 轮换"五层叠加。** 只做首包 padding 无法达标。

### E.1 首包策略(两条路线通用)

1. **保留动态 padding,但改为"拟形 padding"**:不再在固定区间随机,而是让首包长度采样自目标 cover 协议的首包长度分布(如 TLS ClientHello ~517B 或所选伪装的首个记录尺寸)。目标是让首包直方图与真实应用重合,而不是仅仅"不固定"。
2. **首包熵与结构拟形**:token/padding 区用随机字节填充(不要零填充),保证熵接近所选 cover;若走 TLS 路线,首包即真实 ClientHello,天然达标。
3. **握手与首数据包融合保留**,但融合后的总尺寸要落在 cover 首包分布内,避免恒大于真实首包。

### E.2 后续包策略

1. **per-record padding 到目标尺寸分布**:每条记录 pad 到模仿 HTTPS 记录长度的分布;上限设 ~1200~1400B 贴近 MTU,避免 IP 分片。
2. **分段 + 合并**:大消息切成 ≤1200B 块;小消息按目标尺寸批合并(带 5~30ms 上限的批时延),隐藏消息边界与 smux 帧结构。
3. **时序抖动 / pacing**:发送端加抖动、按目标速率整形,打散周期性;keepalive/ping 随机化间隔或藏进数据流,消除周期信号。
4. **加密算法收敛**:删除 XOR;只保留 ChaCha20-Poly1305 / AES-GCM(高熵、无偏置)。
5. **双向对称整形**:上行与下行都做尺寸/时序整形,避免只整一侧导致双向形状不对称而暴露。

### E.3 伪装层选择(主力)

- **首选:TLS 1.3 + 真实域名 + 有效证书**,把隧道承载为 TLS 应用数据(wss 或 HTTP/2 形态),并配**真实站点 fallback** 兜底未授权探测(Reality 思路)。
- **ECH:默认关闭或谨慎使用**(当前是红旗);用 ECH 前先确认目标环境是否已被针对性阻断。
- **高性能模式(可选)**:保留自定义二进制内核,但外包一层"模仿 TLS 记录尺寸 + 时序"的整形层,且仅在无审查/短命链路启用。

### E.4 主动探测与运营

- 未授权访问一律返回真实站点内容(蜜罐/fallback),而非静默。
- 鉴权失败与成功在时延/字节数上不可区分;HMAC 常数时间比较。
- 多 IP DNS 轮询 + 健康检查 + 自动故障切换 + 封禁监控轮换。

### E.5 落地优先级(成本/收益排序)

| 优先级 | 动作 | 成本 | 收益 |
| --- | --- | --- | --- |
| P0 | 删除 XOR;加密收敛到 ChaCha20-Poly1305/AES-GCM | 低 | 消除弱熵指纹 |
| P0 | 主力改 TLS 应用伪装 + 真实站点 fallback | 中 | 大幅降低整体异常度,抗主动探测 |
| P1 | 首包拟形 padding(采样 cover 分布) | 低 | 消除首包长度指纹 |
| P1 | per-record padding + 分段/合并(≤1200B) | 中 | 消除后续包长/消息边界指纹 |
| P2 | 时序抖动/pacing + keepalive 随机化 | 中 | 对抗时序/突发分析 |
| P2 | ECH 默认关闭或可配置,避免红旗 | 低 | 规避 ECH 针对性阻断 |
| P3 | 多 IP 轮换 + 封禁监控运营闭环 | 中 | 提升被封后生存能力 |
| P3 | 空闲 cover traffic(可选) | 高 | 对抗空闲期时序分析,按需启用 |

### E.6 一句话方案

**"首包按 cover 分布拟形 + 后续记录 pad 到 TLS 尺寸并分段合并 + 时序抖动 + 真实站点兜底 + 删 XOR + 多 IP 轮换",主力外形用 TLS 应用伪装,裸二进制仅作可选高性能内核。**

## 附:与现有 x-tunnel(wss + TLS1.3 + ECH)的关系

- 现有 wss 路线方向正确,优于本协议的裸二进制形态;建议本协议向现有 TLS 形态靠拢而非另起裸协议。
- 现有方案需修正点:ECH 默认开 → 建议改为默认关/可配置;补充真实站点 fallback;对 smux 帧做尺寸/时序整形。
- 本协议的"首包融合 + 动态 padding + 静默丢弃"可作为现有 TLS 方案的增强项吸收,而不是独立成一条裸协议路线。
